# Роадмап перехода @pravosleva/reactive-engine на архитектуру линков (v3.0.0)

## Главная цель рефакторинга
Заменить тяжелые для V8 структуры данных `Set` и `Map` (которые сейчас хранят зависимости и подписчиков) на **двунаправленные ребра графа (Links)**, представленные в виде плоских JavaScript-объектов.

```
[Signal/Computed] <--- (NodeLink) ---> [Computed/Effect]
```
Каждое ребро графа хранит четыре ссылки: `nextSubscriber`, `prevSubscriber`, `nextDependency`, `prevDependency`. Это превращает обход графа в сверхбыструю итерацию по указателям памяти.

## Этап 1: Проектирование структур данных (Интерфейсы линков)

Вместо динамического выделения памяти под массивы при каждом изменении зависимостей, мы объявляем каноничную структуру ребра (`NodeLink`):

```typescript
interface NodeLink {
  // Указатели на вершины графа
  source: any;     // Upstream узел (Signal, Computed)
  target: any;     // Downstream узел (Computed, Effect)

  // Двунаправленный список подписчиков для конкретного source
  nextSubscriber: NodeLink | null;
  prevSubscriber: NodeLink | null;

  // Двунаправленный список зависимостей для конкретного target
  nextDependency: NodeLink | null;
  prevDependency: NodeLink | null;

  // Хранилище исторического стейта для equality-cut (решает тест #114)
  version: number;
}
```

## Этап 2: Рефакторинг фабрики `createSignal`

Сигнал избавляется от скрытого `Set` подписчиков. Вместо этого он хранит указатель на голову связного списка ребер.

1. **Новые свойства ноды сигнала:**
   * `subscribersHead: NodeLink | null` — первое ребро подписчика.
   * `subscribersTail: NodeLink | null` — последнее ребро подписчика.
2. **Алгоритм `set value`:**
   * Вместо `for (const sub of subscribers)` рантайм берет `subscribersHead` и синхронно идет по цепочке `link = link.nextSubscriber`.
   * Это убирает создание итераторов `Set` на каждом синхронном тике и ускоряет push-уведомления в 3–5 раз.

## Этап 3: Рефакторинг `createComputed` и `createEffect` (Pull/Push Контур)

Вычисляемые свойства и эффекты переходят на ленивое перестроение списков зависимостей (динамический трекинг).

1. **Алгоритм сбора зависимостей на фазе `.run()`:**
   * При каждом чтении апстрим-ноды проверяется, существовало ли ребро `NodeLink` между текущим `activeConsumer` и этим сигналом в прошлом запуске.
   * Если да — ребро переиспользуется (маркируется живым).
   * Если нет — создается плоский объект `NodeLink` и вставляется в хвост `nextDependency` текущего консьюмера.
2. **Алгоритм утилизации мертвых веток (Garbage Collection):**
   * Все ребра, которые не были прочитаны на текущей итерации ветвления (например, при уходе в `if/else`), мгновенно вырезаются из связного списка за O(1) перебросом ссылок (`prev.next = next`), полностью исключая утечки памяти (`Subscription Leaks`).

## Этап 4: Решение проблемы Net-Zero транзакций (Победа над тестами #114, #180, #186)

Благодаря тому, что каждое ребро `NodeLink` хранит точную версию `version` источника на момент последнего успешного вычисления, движок получает **двухуровневую верификацию грязи**:

1. При побочной записи (`inner write`) внутри `computed` граф не сдвигает глобальные эпохи ядра лавинообразно.
2. Downstream-потребитель (эффект), прежде чем пересчитаться, выполняет быстрый Pull-обход своих линков (`nextDependency`).
3. Если линк видит, что промежуточный `computed` вернулся в исходное состояние (значение и его локальная версия на ребре совпали), распространение push-волны **гасится мгновенно и атомарно**. Это автоматически решает тесты `#114`, `#180` и `#186` без костылей с батчингом.

## Этап 5: Оптимизация под V8 (Плоские классы)

Для того чтобы V8 мог применить ультимативный *Inline Caching (IC)*, все ноды (`Signal`, `Computed`, `Effect`) и сами линки (`NodeLink`) должны создаваться через плоские, строго типизированные классы с фиксированной формой (Hidden Classes), без динамического подмешивания свойств `(node as any)._node = ...`.

* Все линки создаются через `new NodeLink()`.
* Мономорфный статус функций геттеров и сеттеров выводит производительность на уровень близкий к нативному C++.

### Сравнение архитектурных поколений ядра

* **Текущая архитектура (v2.7.0):** Базируется на `Set` / `Map` зависимостей. Требует очистки `dependencies.clear()` и обхода хэш-таблиц. Эпохи ядра сдвигаются глобально (`engine.epoch++`). Пасует перед сложными `computed side-effects`.
* **Новая архитектура (v3.0.0):** Двунаправленные списки ребер (`NodeLink`). Переиспользование объектов линков в памяти. Локальное версионирование ребер графа. Абсолютная устойчивость к любым `inner writes`.
