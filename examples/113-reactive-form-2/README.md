# Анализ производительности / Про `React.StrictMode`

## 🧠 Двойной хук + Режим StrictMode
При монтировании происходи 4 рендера. Причина кроется в самом React-компоненте `Example113.tsx`, а конкретно — в сочетании двух независимых подписок и встроенного режима дебага StrictMode:

```tsx
const form = engine.use(logic.uiBridge); // 🟢 Подписка 1 (Хук)
const { loading, error } = useReactiveValue(logic.submitResource); // 🟢 Подписка 2 (Хук)
```

Каждый раз, когда вы вызываете хук подписки на реактивное значение (будь то `engine.use` или `useReactiveValue`), внутри него под капотом выполняется нативный метод React `useSyncExternalStore` или классическая связка `useState` + `useEffect`.

## Хронология 4-х запусков тела функции компонента:
1. Первый синхронный запуск: React заходит в компонент. `renderCountRef.current` увеличивается с 0 до 1. Инициализируются два хука подписок.
2. Влияние React StrictMode (Первое удвоение): Так как включен StrictMode, React в дев-окружении синхронно запускает тело компонента второй раз подряд, чтобы проверить чистоту функции (Pure Functions Lint). Наш счетчик `renderCountRef.current` увеличивается с 1 до 2.
3. Такт Микрозадачи и Реактивный Батч: На финише микрозадачи (через `queueMicrotask`) наше ядро завершает сборку мастер-моста (Size: 2 в логе). И пускай ресурс `final-submit` не поменялся, сам `ui-master-bridge` зафиксировал переход из стартового неопределенного состояния в стабильное (🟢 Стабильно), о чем честно уведомляет хук `engine.use(logic.uiBridge)`.
4. Вторая волна рендеров от React: Хук получает сигнал от ядра и триггерит обновление компонента. React запускает функцию в третий раз, счетчик прыгает до 3.Влияние React StrictMode (Второе удвоение): Из-за StrictMode этот новый кадр обновления React снова дублирует дважды. Счетчик делает последний инкремент с 3 до 4.

# Как доказать, что граф ядра работает идеально?
Чтобы отсечь дев-шум планировщика React, StrictMode и двойных хуков, и увидеть настоящее, чистое количество рендеров вашего ядра, достаточно провести один из двух тестов:

## Вариант А
Проверка в Продакшн-моде (Production Build)В файле src/main.tsx закомментируйте обертку <React.StrictMode>:
```tsx
// main.tsx
root.render(
  // <React.StrictMode>
    <App />
  // </React.StrictMode>
);
```
Обновите страницу. Вы увидите, что счетчик на экране покажет ровно 2 рендера (1 — маунт пустой функции, 2 — мгновенная синхронизация с мастер-мостом ядра на первом тике микрозадачи). Больше эта цифра меняться при инициализации не будет.

## Вариант Б: Вынос логов рендеринга прямо в консоль
Добавьте обычный `console.log` внутрь компонента рядом со счетчиком, чтобы увидеть, прилетают ли туда реактивные транзакции:
```tsx
export const Example113 = () => {
  const logic = engine.inject(FormUploaderLogic);

  const renderCountRef = useRef(0);
  renderCountRef.current += 1;

  // 🌟 Выводим маркер рендера в консоль
  console.log(`🖥️ [React Render] Кадр №${renderCountRef.current}`);

  const form = engine.use(logic.uiBridge);
  const resourceState = useReactiveValue(logic.submitResource);

  // ... JSX ...
}
```

Вы увидите, что все 4 вызова функции происходят абсолютно синхронно в рамках одной задачи браузера, а логгер ядра REACTIVE TRANSACTION отрабатывает параллельно всего один раз.

## Резюме анализа
Ядро и модернизированный метод resource работают на теоретическом пределе эффективности. То, что при монтировании сложнейшего дерева (где вычисляется 3 шага валидации и пассивный маппинг файлов) ядро генерирует всего одну транзакцию, а не проваливается в циклы бесконечных обновлений — это огромная инженерная победа.

## 🕵️‍♂️ Как различать логи StrictMode в консоли?

Обратите внимание на имя файла и номер строки, из которых прилетает console.log:
1. `Example113.tsx:24` — это **настоящий (боевой)** проход React, когда он выполняет ваш исходный код.
2. `installHook.js:1` — это **проверочный (искусственный)** проход, который StrictMode запускает принудительно. `installHook.js` — это внутренний скрипт расширения **React DevTools** в браузере. Он перехватывает повторный вызов функции, делает его «тихим» (в старых версиях React он даже приглушал цвет логов) и проверяет, не поплыли ли ссылки.

Каждый раз, когда вы видите пару логов подряд: сначала из вашего файла, а следом из `installHook.js` — это гарантированный признак дев-удвоения StrictMode.

# 📑 Руководство по сохранению реактивности: Решение проблем и частые ошибки (Troubleshooting Guide)

Данное руководство содержит разбор ключевых архитектурных ловушек в работе с ленивым Pull/Push-ядром `ReactiveEngine` при интеграции с фреймворками (React, Vue 3, Angular), а также правила, гарантирующие 100% стабильность реактивного графа зависимостей.

## 🛑 Ловушка 1: Потеря реактивности из-за разрушения ссылок (Proxy Stripping)

### Почему это происходит:
Метод `engine.reactive(target)` возвращает глубокую **Proxy-обертку**, которая перехватывает ловушки `get` и `set` для конкретных ключей. Однако сторонние библиотеки или встроенные утилиты фреймворков (например, нативные методы Vue `reactive()`, `toRaw()` или деструктуризация через spread-оператор `...obj` в React) пытаются «снять» Proxy или скопировать свойства в новый плоский объект.
Как только ссылка на оригинальный Proxy теряется, сеттеры ядра перестают перехватывать изменения, батчинг микрозадач `REACTIVE TRANSACTION` замерзает, и граф реактивности безвозвратно рвется.

### Как этого избежать:
* **Никогда не деструктуризируйте реактивные объекты напрямую** в компонентах или эффектах (`const { name } = logic.user` — смерть для подписок).
* Читайте свойства Proxy **всегда через точку** прямо в том месте, где данные рендерятся или вычисляются (`logic.user.name`), чтобы геттер ядра успел зафиксировать активный эффект.
* Для безопасного проброса Proxy-данных в интерфейс React/Vue всегда создавайте плоский **`computed`-мост (UI Bridge)** на стороне сервиса:
```typescript
// ✅ Правильно: Монолитный UI-Bridge на стороне сервиса
public uiBridge = this.engine.computed(() => ({
  name: this.user.name, // Геттер Proxy зафиксирован ядром
  age: this.user.meta.age
}), 'ui-bridge [IS_OPTIMIZED=1]');
```

## ⏳ Ловушка 2: Гонка асинхронных кэшей (Async Context Tracking Desync)

### Почему это происходит:
Глобальный указатель ядра `engine.activeEffect` отслеживает зависимости **строго в синхронном потоке выполнения**. Если внутри реактивного эффекта (`engine.effect`) или вычисляемого свойства (`computed`) вы вызываете асинхронный код (`async/await`, `setTimeout`, `Promise.then`), синхронный поток прерывается.
Когда асинхронный коллбэк возвращает управление спустя 500 мс, указатель `activeEffect` уже равен `null` или переключен на другой эффект. Любые геттеры сигналов или Proxy, вызванные *после* ключевого слова `await`, становятся «слепыми» — ядро не запишет их в зависимости текущего компута.

### Как этого избежать:
* **Правило чистых функций:** Внутри `computed`-свойств категорически запрещено использовать `async/await` и выполнять мутации стейта (Side Effects). Они должны быть строго синхронными, ленивыми и детерминированными.
* **Изолируйте асинхронность в `engine.resource`:** Для любых сетевых запросов используйте фабрику ресурсов.
* **Блокируйте побочные мутации внутри фетчеров:** Внутри асинхронной функции `fetcher` ресурса запрещено императивно менять Proxy-шаги стейт-машины интерфейса (`this.machine.currentStep = 'SUCCESS_PAGE'`). Переключение шагов должно происходить декларативно — внутри синхронного эффекта ядра, который слушает реактивный стейт ресурса:
```typescript
// ✅ Правильно: Синхронный эффект-оркестратор слушает стейт ресурса
private syncWithNetwork = this.engine.effect(() => {
  const res = this.submitResource.value; // Синхронное чтение стейта на финише микрозадачи
  if (res.error) this.machine.currentStep = 'ERROR_PAGE';
  else if (!res.loading && res.data) this.machine.currentStep = 'SUCCESS_PAGE';
}, 'network-bridge [IS_OPTIMIZED=1]');
```

## 🔄 Ловушка 3: Ловушка ленивого кэширования (The Pull-Model "Frozen" Getter)

### Почему это происходит:
Вычисляемые свойства (`computed`) в нашем ядре работают по Pull-модели (ленивое кэширование). Они не пересчитываются сами по себе при изменении сигналов, а просто взводят флаг «грязи» (`isDirty = true`). Перерасчет и логгер сработают **только тогда, когда кто-то физически обратится к свойству `.value`**.
Если фреймворк (например, Vue 3 или Angular) подпишется на `computed` через `.subscribe()`, но в коллбэке подписки адаптера не произойдет принудительного чтения `.value`, ленивый кэш «замерзнет», внешние триггеры (`triggerRef`) не сработают, и DOM-дерево не обновится.

### Как этого избежать:
* Адаптеры фреймворков обязаны синхронизировать Push и Pull модели, принудительно опрашивая геттер ядра внутри коллбэка подписки:
```typescript
// ✅ Правильно: Реализация метода .use() в Vue/Angular адаптерах
const unsubscribe = item.subscribe(() => {
  const freshValue = item.value; // Побуждает ленивый computed пересчитаться и пушить логи!
  frameworkSignal.set(freshValue);
});
```

## 🕸️ Ловушка 4: Циклические зависимости и многослойные каскады (Circular Cascades)

### Почему это происходит:
Выстраивание длинных каскадных цепочек, где `computed` слушает другой `computed`, который слушает третий `computed`, экспоненциально усложняет стабилизацию графа. В момент батчинга микрозадач ленивые кэши промежуточных звеньев начинают «обгонять» друг друга. Это приводит к тому, что финальный мастер-мост считывает устаревший кэш до того, как весь граф успел синхронно обновиться, вызывая «залипание» интерфейса и кнопок (например, `primaryEnabled: false` при валидных полях).

### Как этого избежать:
* **Плоский граф реактивности:** Для простых проверок полей ввода формы («длина > 5», «MIME-тип валиден») не плодите промежуточные `computed`-свойства. Вычисляйте эти условия **синхронно, лениво и атомарно прямо внутри одного единственного мастер-геттера `uiBridge`**, используя чистые функции-валидаторы под-сервисов:
```typescript
// ✅ Правильно: Монолитный плоский UI-Bridge без каскадных race conditions
public uiBridge = this.engine.computed(() => {
  const step1Res = this.step1.checkIsValid(); // Чистый синхронный метод AbstractService
  return {
    appealType: this.step1.fields.appealType,
    step1Error: step1Res.message,
    primaryEnabled: step1Res.isValid // Синхронная и мгновенная активация кнопки!
  };
}, 'ui-master-bridge [IS_OPTIMIZED=1]');
```
## 🗑️ Ловушка 5: Утечки памяти при подписке на ресурсы (Resource Cleanup Failure)

### Почему это происходит:
Когда вы динамически создаете `engine.resource` для каждого индивидуального файла в массиве, ядро регистрирует под капотом долгоживущие эффекты слежения. Если просто удалить файл из Proxy-массива через `.splice()`, сам асинхронный ресурс и его fetch-запрос останутся висеть в памяти ядра и сетевом стеке браузера как «зомби-процессы».

### Как этого избежать:
* Всегда сохраняйте функцию отписки `CleanupFn`, которую возвращает метод `.subscribe()` при создании динамических ресурсов.
* При удалении сущности принудительно вызывайте сохраненный деструктор — это синхронно убьет эффект в ядре и мгновенно прервет HTTP-запрос в браузере через `AbortController` (статус `(canceled)` во вкладке Network):
```typescript
// ✅ Правильно: Точечный авто-abort сетевого запроса при удалении файла
public removeFile(id: string): void {
  const index = this.state.items.findIndex(i => i.id === id);
  if (index === -1) return;

  // Синхронно обрываем fetch соединение и вычищаем эффекты из ядра
  if (typeof this.state.items[index].unsubscribeFn === 'function') {
    this.state.items[index].unsubscribeFn();
  }
  this.state.items.splice(index, 1); // Удаляем из Proxy-массива
}
```
