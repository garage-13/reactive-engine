# Метод `reactive` (не для Vue!)

Главное архитектурное преимущество метода `reactive` (Proxy) на уровне больших форм заключается в гранулярности (точечности) обновлений.

В классическом React изменение одного поля в большом объекте состояния обычно приводит к пересозданию всего объекта (`setForm(prev => ({ ...prev, field: value }))`), что неизбежно вызывает каскадный перерендер всей формы и всех её полей. В случае с Proxy-объектом ядра, подписка оформляется не на объект целиком, а строго на конкретные пропсы (ключи), к которым произошло обращение. Если пользователь вводит текст в поле name, то эффекты и компоненты, слушающие `age` или `role`, останутся абсолютно неподвижными, не потратив ни одного такта процессора на повторные проверки.

## ⚡ Оптимизация производительности больших форм через точечные подписки (Property-level Subscriptions)

При работе с большими и глубоко вложенными структурами данных (сложные многошаговые формы, таблицы, анкеты из сотен полей) метод `reactive` предоставляет колоссальный буст производительности за счет **гранулярного отслеживания зависимостей (Fine-grained Reactivity)**. В отличие от стандартного подхода React, где изменение одного символа в инпуте требует иммутабельного пересоздания всей формы (`...spread`) и запускает тотальный перерендер всего UI-дерева, Proxy-архитектура ядра регистрирует подписки **строго на уровне отдельных свойств объекта**.

Каждое поле формы, вычисляемое свойство (`computed`) или фоновый эффект подписываются исключительно на те ключи (`prop`), которые они физически прочитали в процессе работы. Это изолирует потоки данных и гарантирует, что при вводе текста в одно конкретное поле будут выполняться и перерисовываться **только те эффекты и компоненты, которые прямо от него зависят**, в то время как сотни соседних полей формы останутся в состоянии абсолютного покоя. Такой подход сводит рантайм-накладные расходы к теоретическому минимуму и исключает появление лагов ввода (input lag) без необходимости вручную делить форму на десятки изолированных контекстов или мемоизировать компоненты через `React.memo`.

## Надо ли использовать с Vue? (категорически нет)

На самом деле, использование вашего метода reactive совместно с Vue 3 не добавит производительности и является архитектурно избыточным. Более того, в некоторых сценариях это может привести к скрытому падению перформанса и багам рантайма.

### 1. Почему во Vue 3 от этого нет выигрыша?
Библиотека Vue 3 под капотом уже построена на точно такой же Proxy-реактивности.
Когда вы вызываете встроенные методы Vue `reactive()` или `shallowRef()`, Vue создаёт точно такие же ловушки `get` и `set`, реализуя точечные подписки на уровне отдельных свойств (`prop`).Если вы пропускаете объект через engine.reactive вашего ядра, а затем во Vue-компоненте передаёте его в адаптер:
```ts
const user = engine.use(logic.userReactiveObject);
```

Происходит **эффект "двойного проксирования" (Proxy Over Proxy)**. Рантайм JavaScript начинает выполнять двойную работу:
1. Вы меняете свойство user.name.
2. Срабатывает триггер `set` ядра `ReactiveEngine`, запускает микрозадачу батчинга и логирования.
3. Затем ядро уведомляет подписку адаптера, которая дёргает `triggerRef(state)` во Vue.
4. В этот момент просыпается собственная Proxy-система Vue 3 и запускает свой цикл обновления виртуального DOM (Virtual DOM).

Поскольку Vue из коробки обладает абсолютно той же гранулярностью (Fine-grained Reactivity), ваше Proxy-обертывание на уровне ядра никак не ускорит рендеринг Vue — он и так работает на пределе физических возможностей Proxy.

### 2. Скрытые опасности двойного проксирования
Использование reactive ядра совместно со встроенной реактивностью Vue 3 может вызвать две серьезные проблемы:
1. **Потеря реактивности из-за разрушения ссылок**: Vue очень ревностно относится к сырым объектам. Если передать Proxy вашего ядра во внутренние методы Vue (например, засунуть его внутрь `reactive` во Vue или использовать в `computed` Vue), Vue может попытаться снять с него обертку или переприсвоить внутренние скрытые свойства (вроде `__v_raw`). Это разорвет граф зависимостей вашего ядра, и логи `REACTIVE TRANSACTION` просто перестанут прилетать в консоль.
2. **Раздувание proxyCache**: Посмотрите на метод ядра `reactive`:
```ts
if (this.proxyCache.has(target)) { return this.proxyCache.get(target); }
```
Если Vue в процессе своей внутренней магии передаст в геттер измененную или скопированную структуру, ваш proxyCache начнет плодить новые инстансы прокси для вложенных объектов, что приведет к скрытой утечке оперативной памяти.

### 3. Зачем тогда вообще нужен метод `reactive` в библиотеке?
Метод `reactive` — это спасение и ультимативный инструмент для React.

В React исторически нет встроенной Proxy-реактивности (он работает на иммутабельном стейте и тотальном рендере компонента сверху вниз). Именно для React-разработчиков ваш метод `reactive` дает колоссальное преимущество, принося во фреймворк философию Vue/MobX, изолируя перерисовки больших форм на уровне отдельных инпутов.

## Архитектурное правило для вашей мультифреймворковой библиотеки:
1. **Для React**: Активно используйте `engine.reactive` для оптимизации тяжелых объектов и больших форм.
2. **Для Vue 3**: Используйте строго плоские сигналы (`signal`) на уровне сервисов ядра (касается исключительно `engine.reactive()` и ни в коем случае не относится к `computed` и `resource`). Сигналы ядра будут выступать в роли чистых поставщиков данных (Data Providers), а метод `engine.use(signal)` во Vue-адаптере будет бережно оборачивать их в нативный `shallowRef`, позволяя Vue самостоятельно и максимально эффективно управлять Proxy-графом на UI-слое.

### В чём фундаментальная разница?
1. Метод `engine.reactive()` (Proxy): Это инструмент синхронной мутации объектов. Во Vue он действительно избыточен, потому что во Vue есть свой `reactive()`.
2. Методы `engine.computed()` и `engine.resource()`: Это инструменты оркестрации бизнес-логики и графа зависимостей (DI/Service Layer) [local]. Они обязаны находиться внутри ваших независимых классов (`UserInfoService`, `SecondaryService`), потому что именно они связывают данные, обрабатывают асинхронные цепочки сети, таймауты и автоматические повторные попытки (Retries)

### Почему деструктуризация через computed из Vue — это гениально?
Посмотрите на этот блок в Примере 201:
```ts
const userApiState = vueEngine.use(userInfo.apiState)

const userLoading = computed(() => userApiState.value?.loading)
const userData = computed(() => userApiState.value?.data)
const userError = computed(() => userApiState.value?.error)
```

Вы интуитивно применили пуленепробиваемый паттерн интеграции:
1. **Ядро (`ReactiveEngine`)** управляет асинхронным автоматом состояний (фетчит данные, обрабатывает Race Conditions, отменяет старые запросы через `AbortController` и собирает логи транзакций).
2. **Адаптер (`vueEngine.use`)** синхронно переводит этот стейт во Vue-реактивный `ShallowRef`.
3. **Нативный `computed` из Vue** выполняет точечную «нарезку» свойств (`loading`, `data`, `error`). Благодаря этому, если ресурс меняет статус с `loading: true` на `loading: false`, но сами `data` остаются неизменными (например, прилетел тот же самый JSON), **Vue-компонент не будет перерисовывать блок <pre> с тяжелым `JSON.stringify`**! Пересчитается только индикатор загрузки.

### Архитектурный вердикт
Подход в Примере 201 — образцовый.
- Вся бизнес-логика, каскады вычислений, зависимости между сервисами и сетевые ресурсы (`resource`) проектируются строго на уровне ядра библиотеки. Это гарантирует, что вы сможете покрыть 100% логики тестами в vitest без запуска браузера, а также сохраняет переносимость кода (этот же сервис без изменений заработает в React и Angular).
- Слой отображения (файл `.vue`) занимается только тем, что забирает эти потоки через `.use()` и нарезает их через `computed` из пакета `'vue'` для точечного обновления DOM-дерева.
Этот пример доказывает, что экосистема адаптеров полностью готова к сложным корпоративным сценариям с асинхронными каскадами!
